# ADR-001: Use Elixir Phoenix for API Layer and WebRTC Signaling

**Date:** 2025-11-07
**Status:** Accepted
**Deciders:** Kostiantyn Amurov (Engineering), Product team

---

## Context

InterviewFlow requires a backend that can simultaneously:

1. Serve a conventional REST JSON API for CRUD operations (jobs, candidates, applications)
2. Handle persistent, low-latency WebSocket connections for WebRTC signaling — each active interview session requires a long-lived, bidirectional channel for exchanging SDP offers/answers and ICE candidates between participants
3. Process background jobs (scheduling reminders, triggering AI scoring, syncing calendars) without blocking request handling
4. Scale to hundreds of simultaneous interview sessions during peak recruiting cycles (Q1 and Q4)

We evaluated three options:

### Option A: Node.js (Express + Socket.IO)
- Single-threaded event loop handles WebSocket connections well at low concurrency
- JavaScript shared with frontend reduces context switching for a small team
- Socket.IO adds connection overhead vs raw WebSockets; custom clustering needed for multi-node pub/sub
- Background job story requires external libraries (Bull, BullMQ) with additional Redis coordination
- No process supervision built-in; operational burden for crash recovery

### Option B: Go (net/http + Gorilla WebSocket)
- Gorilla WebSocket is mature and performant
- Goroutines make concurrent connection handling straightforward
- Strong type system and fast compile-cycle for API work
- No built-in framework conventions — would need to assemble routing, middleware, migration tooling, and background jobs separately
- Team has no Go production experience; ramp-up cost is high

### Option C: Elixir 1.16 + Phoenix 1.7
- Built on the Erlang VM (BEAM), designed from the ground up for massive concurrency and fault tolerance
- Phoenix Channels provide a first-class abstraction for WebSocket connections — each channel process is isolated, supervised, and lightweight (under 2KB per process)
- Phoenix PubSub with Redis adapter allows horizontal scaling of channel broadcasts without application-level coordination
- Ecto provides a robust data mapping layer with composable queries and explicit transaction boundaries
- Oban (PostgreSQL-backed job queue) integrates natively with Ecto; no separate queue infrastructure for background jobs
- Guardian provides JWT auth that integrates cleanly with Plug pipelines and Phoenix Channels
- The BEAM's "let it crash" philosophy and OTP supervisor trees make the signaling server self-healing — a crashed channel process does not affect other sessions
- One team member has shipped Elixir in production; remainder have Erlang exposure

---

## Decision

We will use **Elixir 1.16 + Phoenix 1.7** for the API and signaling layer.

The core argument is that Phoenix Channels are architecturally the right tool for WebRTC signaling. Each session's signaling state is naturally modeled as a process: it has a lifecycle (created → negotiating → active → ended), receives messages (join, offer, answer, ice-candidate, leave), and should be isolated from other sessions. The BEAM process model maps directly to this. A crash in one session's channel process is caught by the OTP supervisor and restarted without impacting the 499 other live sessions.

The Oban integration is a secondary factor. Managing interview reminders, AI scoring triggers, and calendar sync as Oban jobs backed by the same PostgreSQL database we already have eliminates the operational overhead of running a separate job queue service (Redis Streams or RabbitMQ) in the MVP phase.

---

## Consequences

### Positive
- Phoenix Channels give us production-grade WebSocket multiplexing out of the box, with built-in Presence tracking (shows who is in the interview room without writing any coordination code)
- Supervisor trees mean the signaling service is self-healing; individual session failures are isolated
- Oban eliminates a separate message broker for background jobs at MVP scale
- Ecto's explicit changesets enforce data integrity at the application layer before hitting PostgreSQL constraints
- Pattern matching and immutable data make the signaling state machine easy to reason about and test

### Negative / Risks
- **Team ramp-up:** Three engineers need to become productive in Elixir. Mitigated by structured pairing, ElixirSchool resources, and starting with well-understood CRUD before touching OTP supervision directly.
- **Hiring pool:** Elixir engineers are less common than Node/Go candidates. We accept this trade-off given the technical fit; senior Erlang/OTP engineers are transferable.
- **Ecosystem maturity for some dependencies:** Some libraries we may need (e.g., WebRTC media server integration) are more mature in Go/Node. We are deliberately not doing media *processing* in Elixir — only signaling — which keeps us on the well-trodden path.
- **Debugging unfamiliarity:** Erlang Observer and `:sys.get_state/1` are powerful but unfamiliar. We will invest in Phoenix LiveDashboard for production observability.

### Neutral
- We will run Phoenix on Cloud Run (not Fly.io / Gigalixir) to align with the GCP-centric infrastructure the company already has for other services. Distributed Erlang clustering is not used in the MVP; horizontal scaling is achieved via Phoenix PubSub + Redis, which works fine in a containerized environment where each instance is ephemeral.
