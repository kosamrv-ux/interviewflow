# ADR-005: Introduce Service Layer Between Controllers and Contexts

**Status:** Accepted  
**Date:** 2026-02-09  
**Deciders:** Engineering Team  
**Categories:** backend, architecture

---

## Context

During the Core Features phase (January–February 2026), we observed that business logic was accumulating in two undesirable locations:

1. **Controllers** — `AiScoreController` contained scoring orchestration logic (build payload, call service, persist, rerank) that should not live in an HTTP handler.
2. **Oban workers** — `TriggerScoringWorker` duplicated parts of the scoring flow from the controller, creating drift between the two code paths.

This made testing difficult (had to mock HTTP context to test scoring) and created inconsistent behavior between synchronous API calls and async job-triggered scoring.

### Forces

- Controllers should be thin: parse/validate input → delegate → render output.
- Oban workers need to call the same business logic without going through HTTP.
- The existing Phoenix Context layer (`InterviewFlow.Scoring`) handles pure data access (Ecto queries) and should remain that way.
- We need a layer between "HTTP/job entry point" and "data access" for orchestration.

---

## Decision

Introduce a **Service** layer sitting between Controllers/Workers and Contexts.

```
HTTP Request → Controller → Service → Context → Repo
Oban Job     → Worker    → Service → Context → Repo
```

### Conventions

- Services live in `lib/interview_flow/<domain>/<name>_service.ex`.
- Services are plain modules (not GenServers, not processes).
- Services may call multiple Contexts and emit Telemetry events.
- Services handle cross-cutting concerns: telemetry, error tracking, logging.
- Services are the unit of integration testing (not controllers).
- Controllers remain thin and use `action_fallback` for error handling.

### First Service

`InterviewFlow.Scoring.ScoreService` was extracted as the first implementation (see commit `refactor(backend): extract ScoreService`).

---

## Consequences

### Positive
- Controllers become thin — easier to read and maintain.
- Oban workers and controllers share identical business logic.
- Services are straightforward to unit-test without HTTP context.
- Telemetry and error tracking are centralized in one place.

### Negative
- Adds an extra layer of indirection.
- Risk of anemic services that just delegate to Contexts — teams must ensure services contain real orchestration logic.

### Mitigation
- Linting rule: controllers must not import `Ecto.Query` directly.
- Code review checklist item: "does this belong in a Service?"
- Credo check added to flag `Repo` calls in controller modules.
