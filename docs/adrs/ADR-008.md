# ADR-008: Multi-Tenancy Implementation — Organization-Scoped Resources

**Status**: Accepted
**Date**: 2026-04-30
**Deciders**: Kostya (lead), Platform team

## Context

InterviewFlow is moving from a single-tenant architecture to a multi-tenant SaaS model.
Enterprise customers require full data isolation: one customer must never be able to
access or observe data belonging to another.

We evaluated three common multi-tenancy approaches:

1. **Separate databases per tenant** — strongest isolation, highest ops complexity
2. **Separate schemas per tenant (PostgreSQL schemas)** — good isolation, complicates Ecto
3. **Shared schema with `org_id` on every table** — simplest to implement, requires discipline

## Decision

We adopt **shared schema with `org_id`** on every resource table, enforced at two layers:

### Layer 1: Plug-level org resolution (`OrgScope`)
Every authenticated API request resolves `current_user.org_id` to a full Organization struct
and assigns it to `conn.assigns[:current_org]`. Controllers receive `org_id` from assigns,
never from request params.

### Layer 2: Context-level scope enforcement
All context functions that list or retrieve records accept an explicit `org_id` argument
and always include `WHERE org_id = $1` in the query. No `Repo.get/2` is used without an
org-scoped lookup wrapper. This is enforced via code review and a custom Credo check
(`InterviewFlow.Checks.UnscannedRepoGet`).

### Role-based access within an org
Within an organization, access is further restricted by user role:
- `owner` — full access including billing and org deletion
- `admin` — manage jobs, candidates, API keys, webhooks
- `member` — create and review interviews
- `viewer` — read-only

### Caching
All cache keys are namespaced with `org_id` prefix: `"org:#{org_id}:resource:#{id}"`.
A bug where org_id was omitted from cache keys (leading to cross-tenant data exposure via
cache) was identified in code review and fixed before any release (see commit history).

## Consequences

**Positive:**
- Single Postgres cluster, low ops overhead
- Easy to query cross-org analytics for internal dashboards (superadmin)
- No schema migration per new customer

**Negative:**
- Requires discipline: every query must include org_id; risky without the Credo check
- Harder to physically isolate data for customers with strict compliance requirements
  (we mitigate this by offering dedicated database add-ons for SOC2 customers)
- Cross-tenant bugs possible if a developer omits the org_id scope

## Alternatives Considered

**Postgres schemas:** Rejected because Ecto's multi-repo or `put_prefix` approach adds
significant complexity to migrations, test setup, and query composition. The discipline
cost of `org_id`-scoped queries is lower than the complexity cost of schema-per-tenant.

**Separate databases:** Rejected for initial implementation due to ops complexity. Re-evaluate
at 500+ enterprise customers if compliance demands increase.
