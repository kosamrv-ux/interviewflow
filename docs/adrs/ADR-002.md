# ADR-002: Use PostgreSQL 15 as Primary Data Store

**Date:** 2025-11-07
**Status:** Accepted
**Deciders:** Kostiantyn Amurov (Engineering), Product team

---

## Context

InterviewFlow manages complex relational data: companies have many jobs, jobs have many applications, applications belong to candidates, and each application progresses through a configurable pipeline with multiple interviews, each generating AI scores and structured feedback. The schema has 12+ entity types with rich referential relationships and non-trivial query patterns:

- Fetch all applications for a job, joined with latest AI score and candidate info, sorted by composite score
- Count applications per pipeline stage for a given job, grouped by recruiter
- Load a candidate's full history across all jobs at a company
- Produce aggregate statistics for dashboard analytics (time-to-hire, pass rates by stage)

We also need:
- ACID transactions for state machine transitions (application.pipeline_stage must be updated atomically with the audit log insertion)
- Full-text search on candidate names, job titles, and notes
- JSON storage for flexible AI score breakdowns and ICE candidate arrays without a separate schema
- Reliable background job storage (Oban uses PostgreSQL advisory locks and SKIP LOCKED)

We evaluated:

### Option A: MongoDB
- Flexible schema is appealing for the evolving AI score breakdown format
- Document model creates data duplication for the relational entities (candidate appears inside every application document vs. normalized)
- Transactions added in v4 but complex multi-document patterns are more cumbersome than SQL joins
- Oban does not support MongoDB; would require a separate job queue infrastructure
- Atlas full-text search is good but introduces a managed dependency we don't need

### Option B: MySQL 8
- Fully ACID, mature, well-supported on Cloud SQL
- JSON column support is less mature than PostgreSQL's JSONB
- `SKIP LOCKED` available in MySQL 8 (Oban compatible), but the ecosystem (Ecto, Oban) is most tested against PostgreSQL
- No native full-text search with ranking as capable as PostgreSQL's `tsvector/tsquery`

### Option C: PostgreSQL 15
- Best-in-class JSONB: indexed, queryable, supports partial updates — perfect for `ai_scores.breakdown`
- `SKIP LOCKED` used by Oban for efficient concurrent job dequeuing
- Full-text search with `tsvector`, GIN indexes, and `ts_rank` covers MVP search needs without Elasticsearch
- Window functions for ranking and analytics (application ranking within a job)
- `GENERATED ALWAYS AS` columns for denormalized search vectors
- `uuid_generate_v4()` (pgcrypto) or `gen_random_uuid()` for distributed-safe PKs
- Native array types (`TEXT[]`, `JSONB[]`) for ICE candidate lists
- Ecto/Postgrex ecosystem is most mature for PostgreSQL; migrations, changesets, and query composition are all well-tested
- Cloud SQL for PostgreSQL is a first-class GCP offering with automated backups, point-in-time recovery, and read replicas

---

## Decision

We will use **PostgreSQL 15** on GCP Cloud SQL as the primary data store.

The Oban dependency is the decisive factor at the margin — since we have committed to Elixir + Oban for background job orchestration (see ADR-001), PostgreSQL is the only viable choice that does not introduce a second database. Having Oban and application data in the same PostgreSQL instance means background job enqueuing and business record updates can occur in the same transaction, which eliminates an entire class of distributed consistency bugs (e.g., a job enqueued for a record that was never committed).

Beyond Oban, JSONB's indexability and PostgreSQL's window functions are genuine technical advantages for the analytics queries that drive the recruiter dashboard.

---

## Consequences

### Positive
- Oban job queue and application data in the same transactional boundary — enqueue-in-transaction eliminates "enqueued job for uncommitted record" bugs
- JSONB for `ai_scores.breakdown` means we can iterate on the scoring rubric schema without database migrations
- Window functions (`RANK() OVER (PARTITION BY job_id ORDER BY composite_score DESC)`) make candidate ranking queries simple and fast
- GIN indexes on JSONB and `tsvector` columns give us search performance without Elasticsearch at MVP scale
- `SKIP LOCKED` enables Oban to scale to multiple Phoenix pods without contention
- Cloud SQL handles backups, failover, and read replica lag monitoring; no DBA needed at MVP stage

### Negative / Risks
- **Vertical scaling ceiling:** PostgreSQL on Cloud SQL has a maximum instance size. At very high read volumes (large enterprise customers with thousands of candidates), we may need read replicas or materialized views for analytics. Mitigated by routing analytics queries to the read replica from day one (Ecto multi-repo pattern).
- **Schema migrations:** Relational schemas require migrations for structural changes. We mitigate with zero-downtime migration patterns: add column → deploy code that writes both old and new → backfill → remove old column. Strong Ecto migration tooling supports this.
- **JSONB abuse risk:** Storing everything in JSONB to avoid migrations is an anti-pattern. We enforce a rule: JSONB only for genuinely variable-structure data (`ai_scores.breakdown`, `video_sessions.metadata`). All business-critical fields are typed columns.

### Neutral
- We will use `UUID` primary keys (`gen_random_uuid()`) throughout. This is slightly less I/O-efficient than sequential integers for B-tree indexes but eliminates ID-guessing security risks and simplifies multi-region data migration if we ever need it.
- PostgreSQL 15 introduced `MERGE` (UPSERT standard SQL) — we will use this for idempotent score upserts in the AI service callback path.
