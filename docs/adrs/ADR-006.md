# ADR-006: Structured JSON Logging with Correlation IDs

**Status:** Accepted  
**Date:** 2026-02-02  
**Deciders:** Engineering Team  
**Categories:** observability, operations

---

## Context

During Phase 1 (Foundation), logging was plain-text Elixir Logger output — suitable for local development but unusable in production log aggregation tools (Datadog, CloudWatch Logs Insights, Loki). Key problems:

1. **No structure** — log lines could not be parsed or indexed by field.
2. **No request tracing** — impossible to correlate log lines from a single HTTP request, an Oban job triggered by that request, and the AI service call made by that job.
3. **No user context** — security events (login failures, score overrides) could not be attributed to a user without grep-and-hope.
4. **GDPR audit concerns** — no reliable way to extract all logs related to a specific user or company for data subject requests.

### Options Considered

| Option | Pros | Cons |
|---|---|---|
| `logger_json` Elixir library | Native Elixir; minimal config | Less actively maintained |
| **`logger_json` (chosen)** | Plug-and-play; Phoenix-aware; community standard | — |
| Custom Logger.Backend | Full control | High implementation cost |
| OpenTelemetry OTLP | Vendor-neutral; supports tracing | Adds significant complexity; requires OTel collector |
| Logstash ECS format | Elasticsearch-native | Couples us to ELK stack |

---

## Decision

Adopt **structured JSON logging** using `logger_json` with two correlation mechanisms:

### 1. Request ID (`X-Request-Id`)
- Assigned per HTTP request (from upstream load balancer or generated)
- Propagated via `RequestId` plug into `Logger.metadata/1`
- Returned to the client in response headers

### 2. Correlation ID (`X-Correlation-Id`)
- Groups related requests across service boundaries
- Passed from Phoenix → Oban job args → AI service HTTP header
- Enables end-to-end trace reconstruction for a single user action

### Log Fields (every line)
```json
{
  "timestamp": "2026-02-02T15:04:23.123Z",
  "level": "info",
  "message": "interview_scheduled",
  "service": "interview_flow_backend",
  "env": "production",
  "request_id": "abc123def456",
  "correlation_id": "xyz789",
  "user_id": "usr-uuid",
  "company_id": "co-uuid"
}
```

Additional domain fields are added per log call (e.g., `application_id`, `score`).

---

## Consequences

### Positive
- All log lines from a request (across HTTP, Oban, AI service) are linkable.
- Datadog log patterns can alert on specific user or company IDs.
- GDPR extraction: `SELECT * FROM logs WHERE user_id = ?` becomes trivial.
- Request latency visible in access logs without APM.

### Negative
- JSON log parsing adds ~2–5µs per log call (negligible).
- Log volume increases ~30% due to repeated metadata fields.
- `correlation_id` must be manually threaded through Oban job args (convention, not enforced).

### Mitigation
- Credo check planned to flag `Logger.info/1` calls without structured metadata.
- Oban job templates include `correlation_id` in base args map.
- Log sampling to be added in a future phase for high-frequency events.
