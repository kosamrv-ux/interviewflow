# ADR-004: Use Oban for Background Job Processing

**Status:** Accepted  
**Date:** 2026-01-12  
**Deciders:** Engineering Team  
**Categories:** backend, infrastructure

---

## Context

InterviewFlow requires reliable asynchronous processing for several latency-sensitive operations:

1. **AI scoring** — submitting transcripts to Gemini and persisting results (10–60s latency)
2. **Email delivery** — interview reminders, invitations, and notifications
3. **Candidate ranking** — recalculating job-level rankings after each new score
4. **Session cleanup** — purging expired video sessions and rotating ICE credentials

These operations cannot run synchronously within the HTTP request cycle without severely degrading the user experience and risking timeout failures.

### Options Considered

| Option | Pros | Cons |
|---|---|---|
| **Oban** (Postgres-backed) | No new infrastructure; ACID guarantees; built-in retries, scheduling, cron | Adds DB load; not ideal for extremely high throughput |
| **Sidekiq** (Redis-backed) | Battle-tested; low latency; rich ecosystem | Ruby-centric; requires Redis to be reliable; at-least-once semantics need care |
| **GenServer queues** | Zero dependencies; native Elixir | No persistence across restarts; no clustering support |
| **AWS SQS** | Highly scalable; managed | External dependency; adds operational complexity; latency overhead |
| **Broadway** | Excellent for streaming pipelines | Overkill for our workload; more complex setup |

---

## Decision

We will use **Oban** for all background job processing.

Oban stores jobs in PostgreSQL alongside application data. This gives us:

- **Durability**: Jobs survive application restarts (stored in Postgres).
- **Transactional enqueueing**: Jobs are enqueued inside the same database transaction as the triggering event (e.g., scoring is enqueued atomically with session end).
- **ACID retries**: Failed jobs are retried with exponential backoff; the retry state is in the same DB we already monitor.
- **Unique jobs**: Prevents duplicate scoring runs for the same session.
- **Cron scheduling**: Native cron syntax for periodic cleanup and batch scoring.
- **No new infrastructure**: We already run Postgres; Redis is used for PubSub and the token blacklist but does not need to be as reliable as a job queue.

### Queue Structure

| Queue | Workers | Concurrency |
|---|---|---|
| `default` | BatchScoringWorker, PurgeExpiredSessionsWorker | 5 |
| `scoring` | TriggerScoringWorker | 10 |
| `notifications` | InterviewReminderWorker, SendInvitationWorker | 20 |

---

## Consequences

### Positive
- Single dependency (Postgres) for both data and jobs simplifies ops.
- Transactional job insertion prevents ghost jobs on rollback.
- Oban Pro (if purchased later) adds pausing, bulk operations, and web UI.

### Negative
- Oban jobs add moderate read/write load to Postgres (pruning, polling).
- Very high-throughput workloads (>10k jobs/min) would require Oban Pro or a dedicated queue.
- Jobs must be idempotent — Oban provides uniqueness guards but callers must verify.

### Mitigation
- Prune completed jobs after 7 days to control table growth.
- Monitor `oban_jobs` table size and index health via the Grafana dashboard.
- Set `max_attempts: 3` by default; use `max_attempts: 1` for one-shot notifications.
