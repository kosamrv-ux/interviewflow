# ADR-003: Use Python AI Scoring Service on GCP Vertex AI

**Date:** 2025-11-10
**Status:** Accepted
**Deciders:** Kostiantyn Amurov (Engineering), Product team

---

## Context

A core differentiator of InterviewFlow is AI-powered candidate assessment: after each interview, the platform produces a structured scorecard that quantifies candidate performance across multiple competencies. This requires:

1. **Transcript analysis** — process the timestamped transcript of the interview conversation
2. **Code evaluation** — assess the correctness, efficiency, and style of code written during the assessment
3. **Structured output** — return a machine-readable scorecard with per-competency scores and written rationale
4. **Rubric customization** — each company can define custom evaluation criteria for their jobs
5. **Audit-ability** — the system must be able to explain why a score was given (regulatory risk in some jurisdictions)

We considered whether to implement this inside the Elixir backend or as a separate service.

### Option A: Elixir + Nx (Numerical Elixir) / Bumblebee
- Bumblebee provides HuggingFace model loading within the Elixir runtime (BERT, GPT-2 class models)
- Keeps the stack uniform; no cross-service communication
- Current Bumblebee model support is limited to smaller open-source models; GPT-4 / Gemini class models require API calls anyway
- Nx + EXLA compilation overhead during deploys is significant
- The AI/ML ecosystem (LangChain, guidance, instructor) is far richer in Python — prompt engineering tooling, structured output parsers, evaluation frameworks

### Option B: Elixir calling OpenAI API directly
- Simple HTTP call to OpenAI from the Phoenix backend
- No separate service to operate
- Tight coupling: scoring logic lives in the Elixir codebase; swapping providers (OpenAI → Gemini → Anthropic) requires Elixir changes and redeploys
- No ability to run scoring experiments independently of the API
- Rate limiting and retry logic in Elixir — reinventing what exists in Python's `tenacity`, `backoff` libraries

### Option C: Python 3.11 FastAPI service + Vertex AI
- Python has the best AI/ML tooling: `langchain`, `instructor`, `google-cloud-aiplatform`, `openai`, `anthropic`
- Decoupled deployment: AI service can be updated, scaled, and canary-deployed independently of the Phoenix API
- Vertex AI (Gemini 1.5 Pro) chosen over OpenAI because: GCP-native (same project, same IAM, no external data egress for sensitive transcript content), multi-modal capability (audio transcripts + code in one prompt), structured JSON output mode (`response_mime_type: "application/json"`)
- FastAPI provides automatic OpenAPI docs, Pydantic schema validation, and async request handling
- Service can be tested in isolation with synthetic transcripts; Phoenix does not need to be running
- Future path: fine-tune a domain-specific model on our scored transcript corpus; Python tooling supports this path natively

---

## Decision

We will implement AI scoring as a **separate Python 3.11 FastAPI service** deployed on Cloud Run, calling **GCP Vertex AI (Gemini 1.5 Pro)** for transcript and code analysis.

The Phoenix backend triggers scoring asynchronously via an Oban job after session end. The Oban job makes an HTTP POST to the AI service using Tesla (Elixir HTTP client). The AI service returns a structured `ScoreBreakdown` JSON, which Phoenix persists as an `AiScore` record. The Phoenix Channel then broadcasts a `scorecard_ready` event to the recruiter's dashboard.

The Vertex AI choice over OpenAI is driven by:
1. **Data residency** — transcripts contain PII. Keeping them within the same GCP project avoids egress to a third-party API and simplifies DPA/GDPR documentation.
2. **IAM-based auth** — no API key to rotate; service account credentials managed by Cloud Run.
3. **Gemini 1.5's context window** — 1M tokens handles even the longest interview transcripts without chunking.

---

## Consequences

### Positive
- AI scoring logic is isolated and independently deployable — we can A/B test prompts, swap models, or retrain without touching the Phoenix codebase
- Python ML ecosystem (`instructor` for structured output, `tenacity` for retry, `google-cloud-aiplatform` for Vertex) is mature and well-supported
- Vertex AI managed service means no GPU infrastructure to manage at MVP
- Service can scale to zero on Cloud Run when no interviews are being processed (scoring jobs are async; latency tolerance is seconds, not milliseconds)
- Pydantic schemas in the AI service serve as a contract between the scoring output and Phoenix's persistence layer — any breaking change in the output schema is caught at deserialization time

### Negative / Risks
- **Network hop:** Phoenix → AI service over HTTPS adds latency to scoring. Acceptable because scoring is async post-session; mitigated by Cloud Run internal networking (Private Google Access) keeping the call within GCP.
- **Operational surface:** One additional Cloud Run service to deploy, monitor, and maintain. Mitigated by keeping the AI service stateless and simple.
- **Vertex AI cost:** Gemini 1.5 Pro input tokens are billed. A 60-minute interview transcript is approximately 8,000 tokens; at current pricing this is ~$0.02 per scoring call. Acceptable at MVP; revisit with fine-tuned smaller model at scale.
- **Prompt injection risk:** Candidate transcripts are untrusted input fed into LLM prompts. We mitigate by: (1) placing transcript content in a clearly delimited section of the prompt, (2) using Vertex AI's structured output mode (JSON schema enforcement), (3) validating all LLM output through Pydantic before writing to DB.

### Neutral
- The AI service API contract (request/response Pydantic schemas) will be published as a shared spec (`docs/rfcs/RFC-002.md`) and versioned independently. Phoenix's Oban job will pin to a specific AI service version via the `X-API-Version` header.
