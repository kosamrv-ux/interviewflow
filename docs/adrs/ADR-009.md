# ADR-009: Enterprise Phase Final Architecture — API Versioning and Integration Strategy

**Status**: Accepted
**Date**: 2026-06-03
**Deciders**: Kostya (lead), Platform team, Enterprise team

## Context

With the v1.0.0 release approaching, the team needed to make several cross-cutting
architectural decisions to stabilize the platform for enterprise customers:

1. **API versioning strategy**: How do we evolve the API without breaking existing integrations?
2. **Integration approach**: Push (webhooks) or pull (polling) for third-party systems?
3. **SSO implementation**: Full SAML library vs. OIDC-only vs. delegate to an identity provider?
4. **Tenant isolation enforcement**: How do we prevent the inevitable developer mistake of
   omitting `org_id` from a query?

## Decisions

### 1. URL-path versioning with long deprecation windows

We use `/api/v1/` → `/api/v2/` URL-path versioning rather than header-based versioning
(`Accept: application/vnd.interviewflow.v2+json`) or query-param versioning (`?version=2`).

**Rationale:**
- URL-path versioning is the most visible and tooling-friendly (curl, Postman, browser, logs)
- Header versioning requires clients to set non-standard headers, increasing integration friction
- We commit to 12+ months of deprecation windows before removing old versions
- Breaking changes are batched into major version bumps (v2 accumulated all breaking changes
  that had built up since v1 launch: timestamp format, response envelope, renamed fields)

V1 deprecation timeline: deprecated 2026-05-01, removed 2027-05-01 (12 months).

### 2. Webhook-first integration (outgoing), structured incoming handlers

For outgoing notifications (events like `interview.completed`, `scoring.done`), we use
webhooks rather than requiring integrators to poll the API. Rationale:

- Polling is wasteful for low-frequency events (most interviews are 30-60 min apart)
- Webhooks are the industry standard for ATS/HRIS integrations (Greenhouse, Lever, Workday all expect them)
- Our Oban-backed delivery with exponential retry gives reliability comparable to a message queue
  without the operational overhead of managing SQS/Pub-Sub

For incoming events (Greenhouse, Slack), we run dedicated handlers that verify HMAC signatures
before processing. All unrecognized event types are acknowledged with 200 and logged — this
prevents integration partners from seeing errors for events we don't yet handle.

### 3. OIDC-first SSO with SAML fallback

We implement SSO via OIDC (OAuth2 + ID token) for Okta, Google Workspace, and Azure AD.
Generic SAML 2.0 is stubbed for customers who require it but not built out for v1.0.

**Rationale:**
- 90%+ of our enterprise prospects use Okta or Google Workspace, both of which support OIDC
- SAML parsing libraries in Elixir are immature; the risk of security vulnerabilities in a
  custom SAML implementation outweighs the benefit for the initial enterprise launch
- OIDC token verification is well-understood (JWT + JWKS) and can be implemented securely
  without external libraries for the happy path
- SAML will be implemented via a dedicated service (likely a Node.js sidecar using `saml2-js`)
  in a future sprint

### 4. Credo check for unscoped Repo access

To enforce the multi-tenancy invariant (every query must include `org_id`), we implemented
a custom Credo check (`InterviewFlow.Checks.UnscannedRepoGet`) that fails CI if any
call to `Repo.get/2`, `Repo.get_by/2`, or `Repo.all/2` is found outside of designated
context modules.

Context modules in `interview_flow/` are permitted to call Repo directly.
Controllers and workers must go through context functions.

This was triggered by an internal review that found two places where controllers were calling
`Repo.get/2` directly, bypassing org scoping. Both were fixed before v1.0 launch.

## Consequences

**Positive:**
- Clear API evolution path with customer-friendly deprecation windows
- Webhook-first reduces infrastructure complexity vs. managed message queues
- OIDC SSO covers the majority of enterprise customers at launch
- Credo check makes the org_id invariant machine-enforceable

**Negative:**
- URL-path versioning means maintaining parallel codebases during transition periods
- Webhook delivery reliability depends on external endpoints being available; dead endpoints
  accumulate failure_count and may flood logs (mitigated by auto-disable at failure threshold)
- SAML customers will need to wait for v1.1 or use OIDC if their IdP supports it
