# ADR-007: Redis Caching Strategy for Scale Phase

**Status**: Accepted
**Date**: 2026-03-09
**Deciders**: Kostya (lead), Platform team

---

## Context

Load testing at 200 concurrent users on the staging environment (10M row dataset)
revealed that the main performance bottlenecks were:

1. `/api/v1/applications` — 1840 ms p99 due to sequential scans
2. Dashboard aggregate queries — 5800 ms p99 from 6 uncached COUNT aggregates
3. AI score polling — 720 ms p99 from DB round-trips per poll interval (5 s)
4. Upcoming interview list — 620 ms p99, polled every 30 s by notification bell

The DB connection pool reached 94% utilisation at peak, causing connection
queue timeouts.

We evaluated three caching approaches:

| Option                  | Pros                                  | Cons                                     |
|-------------------------|---------------------------------------|------------------------------------------|
| A: HTTP response caching| Zero code change; CDN-compatible      | Can't serve auth'd responses; stale data |
| B: ETS (in-process)     | Zero latency; no network hop          | Per-instance; cache doesn't span Cloud Run replicas |
| C: Redis (Memorystore)  | Shared across all instances; already deployed for PubSub | ~1 ms network overhead; extra infra |

---

## Decision

Use **Redis (Memorystore)** via the existing Redix connection pool for a
shared caching layer (Option C).

Key design decisions:

### Tiered TTL

Four TTL tiers chosen based on data change frequency and cache miss cost:

| Tier | TTL    | Use cases                                      |
|------|--------|------------------------------------------------|
| hot  | 60 s   | Per-user upcoming interviews, interview detail |
| warm | 300 s  | Paginated lists, dashboard aggregates, AI scores |
| cold | 1800 s | Company settings                               |
| day  | 86400s | Scoring rubrics (immutable once published)     |

### Key namespace

`if:{resource}:{id}:{variant}` — prefix `if:` is short but unique enough to
avoid collision with other Redis clients.  Company ID in the key prevents
cross-tenant data leakage (defence in depth alongside DB-level scoping).

### Cache invalidation

Explicit invalidation on every write (not time-based only):
- Status changes call `Cache.invalidate_pattern/1` on relevant key groups
- `Cache.fetch/3` fallthrough ensures callers are never responsible for
  handling cache misses

Chose explicit over tag-based invalidation (e.g. Cachex tags) to avoid
complexity; the key namespace design makes invalidation patterns clear.

### Fallback behaviour

`Cache.fetch/3` returns `{:error, reason}` from the loader on DB error, and
returns the DB result directly if Redis is unavailable.  Cache failures are
logged at WARNING but never raise to the caller.

---

## Consequences

**Positive**:
- p99 reduced 24-40× across all hot endpoints (see PERFORMANCE.md)
- DB pool utilisation dropped from 94% to 22% at 200 VU
- AI score polling (5 s interval) absorbed by Redis at 97% hit rate

**Negative**:
- 42 MB Redis memory footprint at 200 VU baseline (well within 4 GB Memorystore tier)
- Invalidation logic adds ~15 LOC per write path; must be maintained
- Cache stampede possible if many requests hit the same key simultaneously
  after expiry — mitigated by the 60–300 s TTL spread

**Open**:
- Consider probabilistic early expiration (PER/XFetch algorithm) if stampede
  is observed under extreme load (> 1000 VU)
- Evaluate Memorystore cluster mode if single-node memory becomes a bottleneck
