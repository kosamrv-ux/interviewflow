# RFC-002: Core API Design

**Date:** 2025-11-10
**Status:** Accepted
**Author:** Kostiantyn Amurov
**Reviewers:** Product team

---

## Summary

This RFC defines the REST API design for InterviewFlow's Phoenix backend. It covers URL structure, authentication strategy, request/response conventions, error handling, and the contract between Phoenix and the Python AI scoring service.

---

## URL Conventions

- All endpoints are versioned: `/api/v1/...`
- Resources are plural nouns: `/jobs`, `/applications`, `/interviews`
- Nested resources are used when the child cannot exist without the parent context, and the nesting depth does not exceed two levels:
  - `/api/v1/jobs/:job_id/applications` — applications are always listed in the context of a job
  - `/api/v1/interviews/:interview_id/sessions` — sessions belong to interviews
- Cross-cutting reads that span multiple parents use top-level resources with filters:
  - `GET /api/v1/applications?stage=interview&assigned_to=me` — not `/jobs/:id/applications` when querying across jobs
- Mutations use standard HTTP verbs; no action-in-URL except for stateful transitions:
  - `PATCH /api/v1/applications/:id/advance` — explicit named action for pipeline stage advancement (avoids clients needing to know valid stage transitions)
  - `POST /api/v1/interviews/:id/cancel` — cancellation is an action, not a field update

## Authentication

**Mechanism:** JWT Bearer tokens via Guardian library.

**Flow:**
1. `POST /api/v1/auth/login` — returns `{access_token, refresh_token, expires_in}`
2. Client includes `Authorization: Bearer <access_token>` on all subsequent requests
3. Access tokens expire in **3600 seconds (1 hour)**
4. Refresh tokens expire in **604800 seconds (7 days)** and are single-use (rotated on each refresh)
5. `POST /api/v1/auth/refresh` — accepts `{refresh_token}`, returns new token pair

**Token claims:**
```json
{
  "sub": "user-uuid",
  "company_id": "company-uuid",
  "role": "recruiter",
  "iat": 1731000000,
  "exp": 1731003600,
  "jti": "unique-token-id"
}
```

**Phoenix Channel auth:** WebSocket join events include `token` in the socket params. The `UserSocket` verifies the JWT and puts `current_user` and `company_id` in socket assigns before any channel join is processed.

**Rate limiting:** Auth endpoints rate-limited at 10 requests/minute per IP using Hammer + Redis. API endpoints rate-limited at 1000 requests/minute per `company_id`.

## Request / Response Conventions

### Content Type
All requests and responses use `application/json`.

### Envelope Format
Successful responses return data directly (no envelope wrapper for single resources, array for collections):

```json
// Single resource
GET /api/v1/jobs/abc-123
{
  "id": "abc-123",
  "title": "Senior Backend Engineer",
  "status": "open",
  ...
}

// Collection
GET /api/v1/jobs
{
  "data": [...],
  "meta": {
    "total": 42,
    "page": 1,
    "per_page": 25
  }
}
```

### Pagination
All list endpoints support cursor-based pagination via `?after=<cursor>&limit=<n>` (max 100). The cursor is an opaque base64-encoded string encoding `{id, inserted_at}` to support stable ordering even as records are inserted.

```json
{
  "data": [...],
  "meta": {
    "total": 142,
    "limit": 25,
    "has_more": true,
    "next_cursor": "eyJpZCI6ImFiYyIsImluc2VydGVkX2F0IjoiMjAyNS0xMS0xMFQxMDowMDowMFoifQ=="
  }
}
```

### Timestamps
All timestamps are returned in ISO 8601 format with UTC timezone: `"2025-11-10T14:30:00Z"`.

### Field Naming
Snake_case for all JSON keys (consistent with Elixir/PostgreSQL conventions). No camelCase.

## Error Handling

All errors return an `errors` array with structured error objects:

```json
// Validation error (422)
{
  "errors": [
    {"field": "title", "message": "can't be blank", "code": "required"},
    {"field": "salary_min", "message": "must be less than salary_max", "code": "invalid"}
  ]
}

// Not found (404)
{
  "errors": [
    {"message": "Job not found", "code": "not_found"}
  ]
}

// Unauthorized (401)
{
  "errors": [
    {"message": "Invalid or expired token", "code": "unauthorized"}
  ]
}

// Forbidden (403)
{
  "errors": [
    {"message": "You don't have permission to perform this action", "code": "forbidden"}
  ]
}

// Rate limited (429)
{
  "errors": [
    {"message": "Too many requests", "code": "rate_limited"}
  ],
  "retry_after": 30
}
```

HTTP status codes follow RESTful conventions:
- `200 OK` — successful read or update
- `201 Created` — successful creation (includes `Location` header)
- `204 No Content` — successful deletion
- `400 Bad Request` — malformed request body
- `401 Unauthorized` — missing or invalid token
- `403 Forbidden` — authenticated but insufficient permissions
- `404 Not Found` — resource does not exist or is not visible to requester
- `409 Conflict` — duplicate resource (e.g., candidate already applied)
- `422 Unprocessable Entity` — validation errors
- `429 Too Many Requests` — rate limited
- `500 Internal Server Error` — unexpected server error

## Full Endpoint Reference

### Auth

| Method | Path | Body | Response | Description |
|--------|------|------|----------|-------------|
| POST | `/api/v1/auth/register` | `{company_name, email, password, full_name}` | 201 `{user, access_token, refresh_token}` | Register new company + admin user |
| POST | `/api/v1/auth/login` | `{email, password}` | 200 `{user, access_token, refresh_token}` | Authenticate user |
| POST | `/api/v1/auth/refresh` | `{refresh_token}` | 200 `{access_token, refresh_token}` | Rotate tokens |
| DELETE | `/api/v1/auth/logout` | — | 204 | Revoke current token |

## Versioning Strategy

- **Current version:** v1 (prefix `/api/v1/`)
- **Breaking changes** (new required fields, removed fields, changed semantics) increment the version: `/api/v2/`
- **Non-breaking additions** (new optional fields, new endpoints) do not require a version bump
- **Version sunset:** v1 will be supported for minimum 12 months after v2 is stable; deprecation notices sent via `Deprecation` and `Sunset` headers
- **AI service versioning:** The `prompt_version` field in the scoring request is used for experiment tracking; the AI service API itself follows semver independently of the Phoenix API version
